### UX-007 — Free-launch policy is not enforced in the implementation financial model

**CODE-SUPPORTED; P1; M (2–4 days for policy/finance reconciliation); OPEN.** Personas: cook, finance operator, customer trust. Surfaces: statement, finance, configuration, ordering. Latest main owner sequence requires zero platform commission/customer fee/paid billing. Implemented `OrderService.java:169` calculates commission from configurable rate; `CommercePolicies.java:33–48` does not enforce launch-zero; `ConfigurationService.java:154` accepts 0..10000bps; `LedgerService.java:33–48` posts snapshot commission; synthetic dev policy sets 1000bps (`backend/app/src/main/resources/db/devdata/R__dev_commerce_policy.sql:3–5`). UI `cook/Statement.tsx:50–81` and `ops/Finance.tsx:53–60` present commission obligations. This is a genuine reconciliation gap, **not proof any real fee was charged**: only synthetic configuration and source were inspected. Preserve historical snapshots; do not zero already accepted orders retroactively. Reconcile decision/rule/backlog/scenario sources; enforce launch policy server-side, then show truthful gross sales, recorded receipt, refund and net-known amount definitions. Acceptance: every newly placed launch order snapshots zero platform charges; nonzero activation is rejected without later owner authorization; duplicate completion remains balanced; no paid-growth controls appear. Regression: launch policy set nonzero in isolated test must be refused; existing immutable-order fixture remains unchanged.

### UX-008 — Approved manual direct-to-kitchen deposit is absent from the current checkout contract

**CODE-SUPPORTED; P1; L (5–10+ days end to end); OPEN.** Customer/cook/support journeys. `Checkout.tsx:384`, native `Cart.tsx:413–415` show COD. Quote and ordering services/contracts have no reviewed deposit receipt/reconciliation states in inspected flow, while latest main `docs/strategy/mvp-direct-deposit-payment.md:14–22` and owner sequence require recipient, deposit, remainder, expiry and separate kitchen acknowledgment/acceptance. Expected: eligible COD and conditional direct deposit with honest report states. Actual: existing implementation cash workflow; deposit remains unavailable. Plan a bounded contract/state/API slice first, then web/cook/ops/native UI. Existing files: quote/order/finance modules, `contracts/openapi.yaml`, existing checkout/order components; future module-local deposit classes only after contract agreement. Acceptance: never call a customer assertion or kitchen statement bank-verified; preparation requires acknowledgment plus acceptance; uncertain transfer never requests automatic second payment; recipient privacy and reconciliation on cancellation. Regression: forged report, amount mismatch, transfer near expiry, kitchen refusal/refund, restart/dedup, cross-kitchen access and all-client totals. Live-money activation stays gated; do not merge a production payment launch as a UX fix.

### UX-001 — Recalculating the quote clears the explicit changed-total consent gate

**VERIFIED in real React/jsdom with synthetic fetch fixture; native CODE-SUPPORTED; P1; S (0.5–1.5 days); OPEN.** Customer web `#/checkout`, native Cart. Web `Checkout.tsx:357–361` normal quote action clears `change`; `:392` requires dedicated acknowledgment only while `change !== null`. Native `Cart.tsx:304–311` clears the same state and `:421` uses the same guard. Reproducer at source cc52fa4: quote q0; change meal price; Place returns 409 PRICE_CHANGED; automatic q1 displays old/new notice; press Calculate total again; notice disappears; tick ordinary terms; Place becomes enabled and submits q1 **without pressing Accept new total**. Component probe passed 1/1 on 2026-10-13 09:18:20 UTC with Node24.21.0/Vitest5.0.3; it proves the component branch with mocked network, not a real financial order. Recommended: bind informed price acceptance to an immutable quote identity/fingerprint; compare every refresh against the last reviewed quote; invalidate ordinary policy consent on a new quote; retain delta until accepted or the checkout is deliberately abandoned. Acceptance: recalculation, retry, second price change, address/mode changes and route return cannot remove a changed-price disclosure or reuse old acceptance; no auto submission; accepted orders preserve snapshots. Regression: exact bypass above in web/native component tests plus real browser/native fixture flow.

### UX-015 — Arabic/Persian numerals fail price input and disappear from OTP input

## WCAG 2.2 AA verification prescription

Run existing real-stack Playwright/axe checks first; retain the current screen-reader BLOCKED state until evidence exists. Map critical routes/forms to these observable acceptance checks:

- 1.3.1, 4.1.2: headings/landmarks/labels, localized table headers, sort states, radio grouping, error associations, meaningful button names.
- 1.4.3, 1.4.11: text4.5:1 (large text3:1) and essential controls/indicators3:1; test actual component backgrounds and both supported themes, not only token pairs.
- 1.4.4, 1.4.10, 1.4.12: 200% text zoom; reflow at320 CSSpx/400% appropriate viewport; text spacing; no lost totals or actions. Tables may use necessary two-dimensional scrolling with labeled keyboard-accessible regions and correct header/cell alignment.
- 2.1.1, 2.1.2, 2.4.3, 2.4.7, 2.4.11: keyboard completion, no traps, logical focus, visible focus and focus not entirely hidden by sticky/fixed bars.
- 2.5.7, 2.5.8: no drag-only essential action; minimum24×24 CSSpx or criterion exceptions; preserve existing44px web target and platform targets rather than reducing them.
- 3.3.1–3.3.4, 3.3.7, 3.3.8: clear corrections and financial confirmation, no unnecessary re-entry of known data, accessible sign-in/OTP/password-manager/paste support, no cognitive puzzle requirement. IdP pages count in the journey.

On Android/iOS separately verify TalkBack/VoiceOver, large text, Arabic/English direction, keyboard avoidance, safe areas, focus on app/browser return and push-denial behavior.
