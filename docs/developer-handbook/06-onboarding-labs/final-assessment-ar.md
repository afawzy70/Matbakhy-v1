# التقييم النهائي

> **Owner role:** Handbook navigation
> **Status:** REFERENCE — قايمة فحص ومعيار تقييم بيحددوا إذا كان المطوّر الجديد جاهز يشتغل باستقلالية.
> **Language / اللغة:** [English](final-assessment.md) · العربية

اللي بيقيّم هو مسؤول صيانة (مش المرشّح). المرشّح بيشتغل من غير مساعد ذكاء اصطناعي، وبيستخدم الـ Repository والدليل بس. كل بند محتاج الدليل المذكور؛ والادعاءات من غير دليل درجتها 0. استخدم بيانات تجريبية بس.

## التقييم

كل معيار من المعايير العشرة بياخد درجة من 0 لـ 3.

| الدرجة | المعنى |
|---|---|
| 0 | ماتثبتش، أو الدليل ناقص، أو اتخرق ثابت من الثوابت |
| 1 | صحيح جزئيًا؛ احتاج مساعدة كبيرة أو تصحيحات |
| 2 | صحيح بفجوات بسيطة اتصلحت أثناء المراجعة |
| 3 | صحيح وكامل وممكن التحقق منه باستقلالية |

**النجاح:** المجموع 24 من 30 على الأقل، ومفيش معيار أقل من 2، والمعايير 6 (كتابة الاختبارات وتشغيلها) و8 (PR مطابق للقواعد) و10 (DOC-001) كل واحد منهم 2 على الأقل. **مشروط:** من 20 لـ 23 من غير أي أصفار: أعد البنود اللي فشلت في خلال أسبوع. **لسه:** أي حاجة غير كده. خرق ثابت (Commit لسر، أو تعديل `main`، أو Merge من غير مراجعة، أو ادّعاء PASS من غير تشغيل) معناه "لسه" أوتوماتيك.

## المعايير

### 1. فهم الـ Domain

معايير النجاح (درجة 3): يذكر الأطراف وإيه اللي مسموح لكل واحد؛ ويسرد الثوابت (EGP بقروش كأرقام صحيحة، والسعر والسعة والأدوار والانتقالات يملكها السيرفر، وطبّاخ واحد وSlot واحد لكل أوردر، وSnapshots غير قابلة للتعديل، والـ Idempotency، والـ Authorization على مستوى الـ Object، وصفر عمولة ولا رسوم منصة في الـ MVP، والدفع كاش عند الاستلام أو عربون يدوي بيبلّغ عنه المطبخ، وعمره ما "متحقق منه بنكيًا"، والعربي RTL والإنجليزي LTR)؛ ويفصل صح بين الـ MVP والنطاق المؤجل.
الدليل: أسئلة وأجوبة شفهية 30 دقيقة متسجّلة في ملاحظات المقيّم؛ ملاحظة اليوم 1؛ والإجابات متطابقة مع [قواعد العمل](../01-business/business-rules-ar.md) و[حالة التنفيذ](../07-reference/implementation-status-ar.md).

### 2. شرح مسارات العميل والمطبخ والموبايل والـ Back Office

النجاح: يمشي في أوردر واحد من الاستكشاف لحد الاكتمال ويسمّي كل شاشة/سطح، والطرف، وتغيير الحالة، ونداءات الـ API اللي وراها، ويقول إيه المختلف في الموبايل والـ Back Office (الاستردادات، وحالات الدعم، وتسوية الكاش، والـ Audit).
الدليل: شرح مباشر على Stack محلي أو بيئة المعاينة بمستخدمين تجريبيين؛ متسق مع [رحلة الأوردر الكاملة](../02-user-journeys/complete-order-journey-ar.md).

### 3. التنقّل في الكود

النجاح: في خلال 10 دقايق يحدد، لتلات ميزات يختارها المقيّم، عملية العقد في `contracts/openapi.yaml`، والـ Controller، والـ Service، والـ Migration/الجدول، والاختبارات.
الدليل: مسارات الملفات مكتوبة لكل واحدة من التلاتة، والمقيّم بيتحقق منها بـ `grep`.

### 4. التشغيل والـ Debug

النجاح: يشغّل الـ Stack من الصفر (`scripts/dev.sh up`، و`smoke`)، ويشغّل تطبيقي الويب، ويقرا Logs الـ API بالـ request id، ويستعلم من الـ Database عن حالة الـ Migrations وعن أوردر معيّن، ويحل عطل واحد محقون (مثلًا بورت مشغول أو ملف env غلط).
الدليل: نسخة من الـ Terminal أو تسجيل شاشة؛ و`scripts/dev.sh smoke` بينتهي بـ PASS؛ والعطل متشرح بالأمر الصح.

### 5. تحديد مكان تنفيذ متطلب عمل

النجاح: بإدخال ID قاعدة (مثلًا BR-018 أو BR-019 أو BR-020) يلاقي نص القاعدة في `planning/rules.json`، والـ Story المالكة، والسيناريوهات الغاطية، والكود اللي بيفرضها، والاختبار اللي بيثبتها.
الدليل: جدول قاعدة ← Story ← سيناريو ← مسار الكود ← اختبار، المقيّم بيتحقق منه؛ وبيعلّم أي قاعدة فرضها في الـ Client بس.

### 6. كتابة الاختبارات وتشغيلها

النجاح: يضيف اختبار بيفشل وبعدين اختبار بينجح لسلوك يختاره المقيّم على المستوى الصح (وحدة، مكوّن، تكامل)؛ ويستخدم PostgreSQL حقيقي لتكامل الـ Backend؛ ويشغّل الاختبار المسمّى بـ `scripts/check_backend_suite.sh` أو أمر اختبار الـ Package؛ ويشرح ليه الاختبار هيمسك Regression.
الدليل: Commit فيه الاختبار؛ مخرجات بتوري أحمر وبعدين أخضر؛ مفيش Mocks للـ Database، ومفيش Assertions اتضعّفت.

### 7. التعامل مع عيب باستقلالية

النجاح: من Issue مكتوب بقالب العيوب (`.github/ISSUE_TEMPLATE/defect.md`) يعمل Reproduce، ويعزل السبب، ويصلّحه، ويضيف اختبار Regression، ويعيد تشغيل الـ Suites المجاورة، ويسجّل الدليل؛ ويقف بعد تلات محاولات فاشلة مختلفة فعلًا ويكتب عائق محدد بدل التخمين.
الدليل: تاريخ الـ Issue أو الـ Branch التدريبي؛ خطوات الـ Reproduction؛ اختبار الـ Regression؛ قايمة الأوامر المشغّلة ونتايجها.

### 8. تقديم PR مطابق للقواعد

النجاح: Branch من `develop` باسم متعارف عليه؛ Commits محددة النطاق؛ الـ PR بيستخدم كل أقسام `.github/pull_request_template.md`؛ والتحقق بيعدّد الأوامر والنتايج وبنود NOT RUN بالظبط؛ ومفيش ادّعاء مراجعة مستقلة؛ وفحوصات الـ CI اتقرت واتعامل معاها؛ ومفيش Merge من المرشّح؛ ومفيش تغييرات على `main`.
الدليل: الـ PR بتاع اليوم 5؛ مخرجات `gh pr checks`؛ قايمة فحص المقيّم مقابل [مسار Git والـ PR](../05-developer-workflow/git-and-pr-workflow-ar.md).

### 9. فهم الـ Deployment لبيئة المعاينة

النجاح: يشرح المسار من develop لـ Product CI لبناء الصور بـ commit SHA لـ Deploy مثبّت بالـ Digest للـ Smoke؛ وبيئة المعاينة هي إيه وهي مش إيه؛ وفئات قايمة الـ IP المسموحة؛ وإيه اللي بيترجّع أوتوماتيك (الإعدادات) وإيه اللي لأ (الـ Database)؛ وإزاي النسخ الاحتياطية و`rollback-plan` بيشتغلوا؛ وإزاي الأسرار بتتبعد عن الـ Repository؛ وإيه اللي بيعمله تجهيز E2E المالك وليه بيستخدم ملف طلب.
الدليل: إجابات شفهية أو مكتوبة متراجعة مقابل [CI/CD](../05-developer-workflow/ci-cd-ar.md) و[بيئة المعاينة](../05-developer-workflow/preview-environment-ar.md)؛ والمرشّح بيشغّل `deploy/web-preview/smoke.sh` للقراءة بس (أو بيقول ليه مش في القايمة المسموحة).

### 10. اتّباع DOC-001

النجاح: يحدد صفحات الدليل المتأثرة بالـ PR باستخدام `docs/developer-handbook/doc001-matrix.json`؛ ويحدّثها بدقة (وسوم IMPLEMENTED/PLANNED/NOT VERIFIED مستخدمة صح، والمسارات حقيقية)؛ و`python3 scripts/doc001_check.py docs` بينجح؛ وكتلة الإقرار صالحة وأمينة؛ وعارف إن السكريبت بيثبت البنية، مش الدقة.
الدليل: Diff لصفحات الدليل؛ مخرجات الفاحص؛ نص الإقرار؛ والمقيّم بيتحقق عشوائيًا من تلات ادعاءات في الصفحات المتغيّرة مقابل الكود.
