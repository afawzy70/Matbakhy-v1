# اليوم 5 - أول مساهمة

> **Owner role:** Handbook navigation
> **Status:** REFERENCE — Lab لتسليم تغيير حقيقي صغير من الأول للآخر تحت قواعد الـ Repository.
> **Language / اللغة:** [English](day-5-first-contribution.md) · العربية

## الأهداف

سلّم تحسين حقيقي ومحدود: دوّر على GitHub issue صغير، وغيّر الكود أو التوثيق، وضيف اختبارات، وحدّث الدليل حسب DOC-001، وافتح PR مطابق للقواعد، ورد على المراجعة.

## قبل ما تبدأ

أعد قراءة [مسار Git والـ PR](../05-developer-workflow/git-and-pr-workflow-ar.md) و[سياسة التوثيق](../05-developer-workflow/documentation-policy-ar.md). القواعد المطبّقة النهارده: ابني على `develop`؛ ماتلمسش `main` أبدًا؛ ماتعملش Merge بنفسك؛ مفيش أسرار ولا بيانات حقيقية؛ ماتضعّفش الاختبارات ولا الأمان.

## الخطوات

1. **اختار Issue حقيقي صغير.** اعرض الموجود؛ وماتفترضش أرقام:
   ```bash
   gh issue list --state open --limit 50
   gh label list
   gh issue list --state open --label <label-from-the-list-above>
   ```
   فضّل Issue يتعمله Reproduce، ومحصور في موديول أو سطح واحد، وممكن يتصلّح في كام ساعة، ومفيهوش قرار معلّق من المالك. الـ Labels بتختلف: استخدم اللي قايمة الـ Labels بتعرضه للشغل الصغير أو التوثيق أو العيوب أو على طريقة "good first". لو مفيش حاجة مناسبة، اطلب من المالك يشاورلك على واحد؛ وعيب في الدليل نفسه تلاقيه في الأيام 1-4 بيتحسب كمان (افتح الـ Issue الأول). ابعد عن أي حاجة بتلمس حركة الفلوس أو قواعد الـ Authorization أو Migrations على جداول مشتركة أو سكريبتات الـ Deployment في أول تغيير.
2. **افهمه.** اعمل Reproduce للمشكلة محليًا (الـ Stack من [البيئة المحلية](../05-developer-workflow/local-environment-ar.md)). دوّر على الكود بأسلوب اليوم 3. حدّد قاعدة العمل أو السيناريو المعني (`planning/rules.json`، `planning/scenarios.json`) وصفحات الدليل اللي بتوصف المنطقة (استخدم `docs/developer-handbook/doc001-matrix.json` عشان تشوف الصفحات اللي المنطقة بتتربط بيها).
3. **خطّط في الـ Issue.** علّق بـ: خطوات الـ Reproduction، والسلوك المقصود، والملفات اللي متوقع تغيّرها، والاختبارات اللي هتضيفها، وصفحات الدليل المتأثرة. استنى الموافقة لو النطاق مش واضح.
4. **الـ Branch.** `git fetch origin && git switch -c <kind>/<short-description> origin/develop`.
5. **الاختبار الأول لو ممكن.** اكتب اختبار بيفشل بيمسك العيب أو السلوك الجديد (وحدة، أو مكوّن، أو `@IntegrationTest` حسب المناسب). شغّله واحتفظ بمخرجات الفشل.
6. **نفّذ.** أصغر تغيير ينجّح الاختبار. خلّي القواعد اللي يملكها السيرفر على السيرفر؛ وخلّي الفلوس بالقروش كأرقام صحيحة؛ وماتكرّرش منطق العمل في Client.
7. **تحقق.** شغّل الـ Suites المتأثرة والمجاورة ليها ([تشغيل الاختبارات](../05-developer-workflow/test-execution-ar.md))، بالإضافة لـ `pnpm contract:check` لو العقود اتغيّرت و`python3 scripts/validate_blueprint.py` لو التخطيط اتغيّر. سجّل الأوامر بالظبط والنتايج؛ واعمل قايمة بأي حاجة ماقدرتش تشغّلها على إنها NOT RUN.
8. **حدّث الدليل (DOC-001).** غيّر كل صفحة دليل المصفوفة بتسميها للمنطقة اللي لمستها، وأي صفحة تانية بقت بتقول حاجة مش صحيحة. خلّي ترويسة الصفحة (الدور المالك، والحالة) صح. شغّل:
   ```bash
   python3 scripts/doc001_check.py docs
   ```
   لو تغييرك فعلًا مش محتاج تغيير في التوثيق، لازم تقول كده بتبرير محدد؛ وده بيحكم عليه مراجع، مش السكريبت.
9. **الـ Commit.** Commits محددة النطاق برسائل واضحة؛ ومن غير تعديلات مالهاش علاقة.
10. **افتح الـ PR** على `develop`: `gh pr create --base develop`. املا كل أقسام القالب (المشكلة؛ التغييرات؛ التحقق بأوامر ونتايج حقيقية؛ المراجعة والمخاطر) و**إقرار Documentation Impact** بالظبط زي ما هو متحدد في [documentation-policy.md](../05-developer-workflow/documentation-policy-ar.md) بين `<!-- DOC-001:BEGIN -->` و`<!-- DOC-001:END -->`. اربط الـ Issue. قول بأمانة إيه اللي ماشغّلتوش. ماتدّعيش إن في مراجعة مستقلة.
11. **افحص الـ CI.** `gh pr checks` لحد ما الـ Jobs المطلوبة تخلص؛ واقرا الفشل بـ `gh run view <run-id> --log-failed` وصلّحه بـ Commits جديدة (من غير force-push).
12. **رد على المراجعة.** جاوب على كل تعليق: صلّحه، أو اشرح بدليل ليه لأ. أعد تشغيل الفحوصات المتأثرة بعد التغييرات وحدّث قسم التحقق في الـ PR. لو مراجع لقى عدم دقة في التوثيق، صلّح الصفحة في نفس الـ PR. ماتعملش Merge؛ المالك أو مسؤول صيانة مخوّل هو اللي يقرر.

## المُخرَج

PR مفتوح (أو Draft PR لو المالك فضّل كده) فيه: Issue حقيقي مربوط؛ اختبار آلي واحد على الأقل جديد أو متغيّر؛ تحديثات للدليل أو تبرير يقنع المراجع؛ إقرار DOC-001 مكتمل؛ فحوصات مطلوبة خضرا أو قايمة أمينة بالفاشلة؛ وردودك على تعليقات المراجعة.

## فحص ذاتي

- [ ] الـ Issue حقيقي وماخترعتش أرقام ولا معايير قبول.
- [ ] الاختبار بتاعي بيفشل من غير التغيير وبينجح بيه.
- [ ] `python3 scripts/doc001_check.py docs` بينجح والصفحات بتقول اللي الكود بيعمله.
- [ ] الـ PR بيعدّد بالظبط اللي شغّلته واللي ماشغّلتوش.
- [ ] مفيش أسرار ولا بيانات حقيقية ولا تعديلات مالهاش علاقة في الـ Diff (`git diff origin/develop --stat`).
- [ ] ماحطيتش إيدي على `main`، وماعملتش Merge.

وبعدين اعمل [التقييم النهائي](final-assessment-ar.md).
