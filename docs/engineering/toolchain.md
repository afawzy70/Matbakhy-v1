## Native builds

Android native compilation needs the Android SDK, platform tools and a JDK supported by the Android Gradle Plugin. iOS needs macOS with the Xcode version supported by Expo SDK 57 and CocoaPods. Generate the native projects with `pnpm exec expo prebuild` inside `apps/customer-mobile`, then build with Gradle or Xcode. Native compilation is part of MB-005's acceptance. `.github/workflows/native-build.yml` compiles it on GitHub-hosted runners: an Android debug APK on ubuntu-24.04 (JDK 17, preinstalled SDK, Gradle 9.3.1) and an unsigned iOS simulator build on macos-26. Xcode 16.4 (macos-15) fails for Expo SDK 57 in the ExpoModulesJSI build phase. The development container cannot do native builds (Android SDK host denied, no macOS). JavaScript bundles, Expo Go or web preview never count as native compilation or device verification.

## Environment notes (development container, 2026-10-11)

- Maven Central intermittently returned HTTP 429 to this container. A machine-local `~/.m2/settings.xml` mirror of Central (Google Cloud mirror) was used; the repository build itself references only Maven Central. For the wrapper download set `MVNW_REPOURL` to a Central mirror if needed.
- `dl.google.com` (Android SDK) is denied by this container's network policy, so Android native builds are BLOCKED here. iOS builds need macOS and are BLOCKED on Linux.
- `exp.host` is not resolvable here, so the two networked `expo-doctor` checks (config schema, React Native Directory) cannot run. The other 19 checks, including the SDK version match and the duplicate-dependency check, passed.

## Backend modules and database tests (MB-006)

- Domain modules are Maven modules under `backend/modules/` (identity, cooks, catalog, availability, orders, finance, support, notifications, operations). Each declares `@DomainModule` on its root package. Other modules may use only its `api` package. `ModuleBoundaryTest` enforces API-only access, no module cycles, `shared` free of module/app dependencies, and modules free of `app` dependencies; deliberately violating fixtures prove the rules fail.
- Flyway owns the schema (`backend/app/src/main/resources/db/migration`, forward-only `V<n>__*.sql`). Synthetic fixtures live in `db/devdata` and load only with the `dev` profile; `EnvironmentGuard` refuses the `dev` profile or fixture locations in STAGING/PRODUCTION.
- `APP_ENV` (LOCAL, CI, STAGING, PRODUCTION) is required; startup fails without it. Datasource: `DATABASE_URL`, `DATABASE_USERNAME`, `DATABASE_PASSWORD`.
- Integration tests use Testcontainers with `postgres:16.15-alpine` pinned by digest (`postgres.test.image` in `backend/pom.xml`), so **Docker must be running** for `./mvnw verify`. There is no H2 or mock-database fallback.
- API errors use the body `{code, messageKey, fieldErrors, requestId, retryable}` with stable codes in `ErrorCode`. `X-Request-Id` is accepted when well-formed, otherwise generated, and always echoed.

## Local stack (MB-008)

`scripts/dev.sh` (bash; Linux, macOS, or WSL2 on Windows):

| Command | Effect |
|---|---|
| `scripts/dev.sh doctor` | Checks Docker CLI/daemon, Compose v2, JDK 21, pinned Node, pnpm, curl, openssl; names every missing item and starts nothing |
| `scripts/dev.sh up` | Creates `infra/.env` from `infra/.env.example` with random local passwords (first run), builds the API jar, starts the stack and waits for health |
| `scripts/dev.sh smoke` | API health, Flyway baseline, Keycloak `matbakhy` realm OIDC discovery, S3 buckets, mail sink capture of a synthetic message, PKCE enforced for the native client, anonymous `/api/v1/me` is 401, and a full web OIDC login through the API returning the profile |
| `scripts/dev.sh down` / `reset` | Stop / stop and delete the data volume; refuses env files not marked `MATBAKHY_ENV_MARKER=local` |
| `scripts/dev.sh verify` | All of the above in a throwaway compose project on alternate ports, then removes it (P01-CHECK-3) |

Services (`infra/compose.yaml`, ports bound to 127.0.0.1, images pinned by digest): PostgreSQL 16.15 (5432), Keycloak 26.8.0 dev mode with realm import from `infra/identity` (8180), Adobe S3Mock 5.2.3 as a local S3 emulator (9090, buckets `matbakhy-private` and `matbakhy-public`), Mailpit 1.31.5 mail sink (UI 8025, SMTP 1025) and the API (8080). The API image (`backend/Dockerfile`) copies the jar built on the host and runs as a non-root user on Temurin 21 JRE.

Secret scan: `scripts/check_secrets.sh` runs Gitleaks 8.30.1 (digest-pinned image) over the full history and working tree (P01-CHECK-4).

CI (`.github/workflows/ci.yml`): clean-checkout workspace check, local stack verify and secret scan on every push and PR. It uses only the SHA-pinned checkout action; Node is downloaded from nodejs.org and checked against a recorded SHA-256, and JDK 21 is the runner's preinstalled toolchain.

Windows: PowerShell equivalents are not provided yet. No PowerShell runtime was available to test them, and untested scripts are not published (BLK-002). Use WSL2 with Docker Desktop meanwhile.

Local identity (MB-009): `infra/identity/matbakhy-realm.json` is a template with the `matbakhy-web` confidential client, the `matbakhy-mobile` public PKCE client and two synthetic users (`customer-a`, `customer-b`). `scripts/dev.sh up` fills in a generated client secret and a synthetic user password from `infra/.env` and writes the result to `infra/.generated/` (ignored by Git). The local user password is in `infra/.env` as `DEV_USER_PASSWORD`. Backend identity tests start their own Keycloak container from the same digest-pinned image, with per-run random secrets.
